# Bloom — Guided Encouragement

**Guided Encouragement** is a real feature from [Bloom](https://muffin.co.jp), muffin Inc.'s puzzle-RPG for mental wellness (Unity, iOS/Android). After clearing a stage, the player labels how they feel — a light *affect labeling* moment — and receives a short, warm encouragement matched to that feeling from Mamorin, Bloom's sleep-loving mascot, generated by Claude. This repo is a portfolio prototype of that feature: the web UI simulates Bloom's post-stage screen, while the API route is built as the actual production-shaped service the Unity client would call — same contract, streaming, and the API key never leaves the server.

## Architecture

```
┌──────────────────────┐      POST /api/encourage       ┌──────────────────┐
│ Unity client (Bloom) │ ────────────────────────────▶  │ This repo         │
│ (the web UI stands   │ ◀────────────────────────────  │ Next.js route     │
│  in for it here)     │      SSE token stream          │ handler           │
└──────────────────────┘                                └────────┬─────────┘
                                                                 │
                                              1. distress check  │ 2. encouragement
                                              (claude-haiku-4-5) │ (claude-sonnet-5)
                                                                 ▼
                                                        ┌──────────────────┐
                                                        │    Claude API    │
                                                        └──────────────────┘
```

The web page in `app/page.tsx` is only a stand-in client for development and demos. Everything that matters for production lives behind `POST /api/encourage`: request validation, rate limiting, the two-step safety design, and SSE streaming. `ANTHROPIC_API_KEY` is read from server env only and is never part of the client bundle.

## API contract

### `POST /api/encourage`

Request body (`application/json`):

```ts
{
  stageId: string;   // e.g. "stage-3-2" (simple identifier)
  feeling: "proud" | "relieved" | "frustrated" | "disappointed"
         | "anxious" | "tired" | "custom";
  freeText?: string; // optional player-written note, max 200 chars
  locale: "en";      // English only for now; field kept for future i18n
}
```

Success response: `200` with `Content-Type: text/event-stream`. The stream is identical for both response paths:

```
event: meta
data: {"type":"encouragement"}        // or {"type":"support"}

event: token
data: {"text":"It makes sense "}      // repeated, one frame per chunk

event: done
data: {}
```

On a mid-stream failure the server emits a friendly `error` event (never a stack trace) followed by `done`:

```
event: error
data: {"message":"Mamorin is having a little nap and couldn't hear you just now. ..."}
```

Error responses (JSON, non-streaming): `400` invalid body, `429` rate limited (10 requests/minute per IP — in-memory for the demo; production would use Redis/Upstash), `503` service not configured.

## Unity client sketch

How Bloom's Unity client consumes the same endpoint — `UnityWebRequest` with a `DownloadHandlerScript` that receives the SSE bytes incrementally (illustrative, not production code):

```csharp
class SseDownloadHandler : DownloadHandlerScript
{
    public event Action<string> OnToken; // parse frames like the web client
    protected override bool ReceiveData(byte[] data, int length)
    {
        ParseSseFrames(Encoding.UTF8.GetString(data, 0, length), OnToken);
        return true;
    }
}

var request = new UnityWebRequest($"{BaseUrl}/api/encourage", "POST");
request.uploadHandler = new UploadHandlerRaw(
    Encoding.UTF8.GetBytes(JsonUtility.ToJson(payload)));
request.downloadHandler = new SseDownloadHandler();
request.SetRequestHeader("Content-Type", "application/json");
yield return request.SendWebRequest(); // tokens arrive via OnToken as Mamorin speaks
```

## Safety design

This is a wellness product, so the route never generates encouragement blindly:

1. **Distress check first.** Every request with a player-written note runs a fast, cheap classification call (`claude-haiku-4-5`, structured outputs pinned to `{"distress": boolean}`) before any encouragement is generated. It distinguishes serious distress — self-harm, hopelessness, crisis — from ordinary game frustration ("this stage is annoying" is not distress). Preset feeling chips alone can't express crisis (they come from our own fixed list), so chip-only requests skip the call. If the classifier's reply can't be parsed, the route fails safe toward the support path.
2. **Static support response.** When distress is flagged, no LLM text is generated. The player receives a fixed, pre-written message (`lib/supportMessage.ts`) that gently acknowledges them, is honest that Bloom is just a game and can't support what they're going through, and encourages reaching out to someone they trust or a professional support service in their area. It's static on purpose: a player in a difficult moment should always get the same carefully reviewed words — no clinical language, no diagnosis, no unpredictable phrasing. It streams through the same SSE format with a `type: "support"` marker so the UI renders it in a calmer style.
3. **Prompt-injection handling.** `freeText` is validated (max 200 chars), fenced in the prompt, and explicitly labelled untrusted player input. The system prompt (`lib/prompts/encouragement.ts`) instructs Mamorin to disregard any instructions inside the note and respond only in persona to the selected feeling. The system prompt lives in its own file so the upcoming eval harness can import and regression-test it.

## Setup

```bash
cp .env.example .env.local   # then add your ANTHROPIC_API_KEY
npm install
npm run dev                  # http://localhost:3000
```

Other scripts: `npm test` (unit tests — validation and distress routing, Anthropic client mocked), `npm run lint`, `npm run build`.
